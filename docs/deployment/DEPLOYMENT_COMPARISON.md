# 部署方式选择指南

## 快速决策

```
┌─────────────────────────────────┐
│  是生产环境且需要高可用吗？        │
└──────────┬──────────────────────┘
           │
    ┌──────┴──────┐
    │             │
   是            否
    │             │
    │             └──► 使用传统部署 (deploy.sh)
    │                  ✓ 简单直接
    │                  ✓ 资源占用少
    │                  ✓ 适合开发/测试
    │
    └──► 使用零停机部署 (deploy-zero-downtime.sh)
         ✓ 无服务中断
         ✓ 快速回滚
         ✓ 适合生产环境
```

## 两种部署方式对比

### 传统部署 (deploy.sh)

**特点**：
- ⚠️ 有 1-2 分钟停机时间
- ✅ 配置简单，易于理解
- ✅ 资源占用低（单容器）
- ⚠️ 回滚需要重新构建（慢）

**适用场景**：
- 开发和测试环境
- 低流量应用
- 可接受短暂停机
- 资源有限的服务器

**快速开始**：
```bash
./deploy.sh
```

---

### 零停机部署 (deploy-zero-downtime.sh)

**特点**：
- ✅ 完全零停机（0秒中断）
- ✅ 秒级回滚
- ✅ 用户无感知更新
- ⚠️ 配置较复杂（自动生成）
- ⚠️ 部署时需要双倍资源

**适用场景**：
- 生产环境
- 高可用要求
- 24/7 服务
- 高流量应用

**快速开始**：
```bash
# 首次使用（会自动创建配置）
./deploy-zero-downtime.sh

# 后续更新
./deploy-zero-downtime.sh

# 快速回滚
./deploy-zero-downtime.sh --rollback
```

## 详细对比表

| 特性 | 传统部署 | 零停机部署 |
|------|---------|-----------|
| **停机时间** | ⚠️ 1-2 分钟 | ✅ 0 秒 |
| **用户体验** | ❌ 服务中断 | ✅ 无感知 |
| **部署流程** | 停止 → 构建 → 启动 | 构建 → 启动新容器 → 切换流量 → 停止旧容器 |
| **回滚速度** | ⚠️ 5-10 分钟（需重新构建） | ✅ 5-10 秒（即时切换） |
| **资源占用** | ✅ 低（单容器） | ⚠️ 中（部署时双容器） |
| **配置复杂度** | ✅ 简单（1个文件） | ⚠️ 中等（3个文件，自动生成） |
| **最低配置** | 2核 CPU, 4GB 内存 | 4核 CPU, 8GB 内存 |
| **推荐配置** | 4核 CPU, 8GB 内存 | 8核 CPU, 16GB 内存 |
| **备份机制** | ✅ 镜像备份 | ✅ 容器保留 |
| **健康检查** | ✅ 支持 | ✅ 支持（更严格） |
| **流量切换** | ❌ 无（直接替换） | ✅ 有（Nginx 代理） |
| **灰度发布** | ❌ 不支持 | ✅ 支持（手动配置） |
| **数据库迁移** | ✅ 简单（可以停机） | ⚠️ 需要兼容性考虑 |

## 部署流程对比

### 传统部署流程

```
1. 检查环境 ✓
2. 拉取代码 ✓
3. 备份镜像 ✓
4. 构建新镜像 ✓
5. 停止旧容器 ⚠️ ← 服务中断开始
6. 启动新容器 ⚠️
7. 健康检查 ⚠️ ← 服务中断结束
8. 完成 ✓

总停机时间: 60-120 秒
```

### 零停机部署流程

```
1. 检查环境 ✓
2. 拉取代码 ✓
3. 检测当前容器 ✓ (Blue/Green)
4. 构建新镜像 ✓
5. 启动新容器 ✓ (与旧容器并存)
6. 健康检查 ✓ (新容器)
7. 切换流量 ✓ (Nginx reload，0停机)
8. 等待连接排空 ✓ (5秒)
9. 停止旧容器 ✓
10. 完成 ✓

总停机时间: 0 秒
```

## 迁移指南

### 从传统部署迁移到零停机部署

```bash
# 1. 停止当前部署
docker-compose down

# 2. 清理旧容器（保留数据）
docker rm -f genio-backend 2>/dev/null || true

# 3. 开始零停机部署（自动创建配置）
./deploy-zero-downtime.sh
```

### 从零停机部署回退到传统部署

```bash
# 1. 停止零停机部署的所有容器
docker-compose -f docker-compose.zero-downtime.yml down

# 2. 使用传统部署
./deploy.sh
```

## 常见问题

### Q1: 零停机部署需要什么额外配置？

**A**: 不需要！首次运行时脚本会自动创建：
- `nginx.conf` - Nginx 配置
- `docker-compose.zero-downtime.yml` - Docker 编排文件

### Q2: 零停机部署是否完全没有风险？

**A**: 几乎无风险，但需要注意：
- 数据库迁移需要向后兼容
- 长连接（WebSocket）可能需要重连
- 部署期间需要双倍容器资源

### Q3: 回滚时数据会丢失吗？

**A**: 不会。因为：
- 数据库和 Redis 是共享的
- 只是切换应用容器版本
- 数据层不受影响

### Q4: 能否混合使用两种部署方式？

**A**: 可以，但不推荐：
- 两种方式使用不同的容器命名
- 需要手动清理才能切换
- 容易产生配置混乱

### Q5: 零停机部署失败会怎样？

**A**: 完全安全：
- 新容器健康检查失败会自动清理
- 旧容器继续提供服务
- 不影响用户访问

## 性能影响

### 传统部署

**部署期间**：
- CPU: 100%（构建期间）
- 内存: 1x 应用容器
- 网络: 服务完全不可用

**部署后**：
- CPU: 正常
- 内存: 正常
- 网络: 正常

### 零停机部署

**部署期间**：
- CPU: 150%（构建 + 双容器）
- 内存: 2x 应用容器（1-2 分钟）
- 网络: 服务持续可用

**部署后**：
- CPU: 正常
- 内存: 正常（旧容器已停止）
- 网络: 正常

## 决策建议

### 选择传统部署，如果：
- ✓ 是开发或测试环境
- ✓ 流量较低，用户较少
- ✓ 可以接受短暂停机
- ✓ 服务器资源有限
- ✓ 追求配置简单

### 选择零停机部署，如果：
- ✓ 是生产环境
- ✓ 需要 24/7 可用性
- ✓ 用户体验要求高
- ✓ 服务器资源充足
- ✓ 需要快速回滚能力

## 总结

| 场景 | 推荐方案 | 理由 |
|-----|---------|------|
| 开发环境 | 传统部署 | 简单快速，资源占用少 |
| 测试环境 | 零停机部署 | 模拟生产环境 |
| 生产环境（小流量） | 传统部署 | 成本低，可接受短暂停机 |
| 生产环境（高流量） | 零停机部署 | 必须保证可用性 |
| SaaS 服务 | 零停机部署 | 用户体验第一 |
| 内部系统 | 传统部署 | 可在非工作时间部署 |
